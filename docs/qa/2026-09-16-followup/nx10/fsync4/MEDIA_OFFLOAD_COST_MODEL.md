## 1. 질문을 두 개로 쪼갠다 — 왜 “단위”만 물으면 답이 안 나오는가

D-F3-2 는 “`media` 를 준다면 **단위**(대화별 옵트인 / 전역 주기 / 제공 안 함)”를 묻는다. 그런데 §35-2 는
`media` 가 커밋마다 줄 수 없다(242 %)는 것까지만 말했다 — **핫패스 밖에서 돌리면 정말 핫패스가 무사한가**는
아무도 안 쟀다. 그래서 이 문서는 단위를 정하기 전에 두 가지를 나눠 잰다.

| 물음 | 잴 것 | 어디서 |
| --- | --- | --- |
| **얼마인가** | 호출 1회의 비용과 **커밋당 상각** (주기·체크포인트·셧다운 각각) | §2 · §3 |
| **누가 멈추는가** | 배경에서 부른 `media` 가 **돌고 있는 쓰는 쪽**을 멈추는가 | §4 |

두 답이 다르면(그럴 것이다) 결정은 “어느 단위인가”가 아니라 **“언제 부르는가”** 로 옮겨 간다 — §5.

## 2. 비용 모델 — 호출은 **부피와 무관한 배리어**다

커밋 `k`개를 sync 없이 쌓고 `F_FULLFSYNC` **1회**(교차 반복 4회 → **최소값**; 최소값이 오염이 가장 적은 추정이다).

| `k` | 바이트 | run A | run B | 커밋당 상각 A / B |
| --- | --- | --- | --- | --- |
| 1 | 271 B | 6,301 µs | 6,098 µs | — |
| 8 | 2.2 KB | 4,739 | 3,784 | 592 / 473 µs |
| **32** | 8.7 KB | **7,569** | **7,862** | 237 / 246 µs |
| 128 | 35 KB | 4,124 | 4,216 | **32.220 / 32.938 µs** |
| 512 | 139 KB | 3,570 | 3,344 | 6.972 / 6.530 µs |
| 2,048 | 555 KB | 3,694 | 3,501 | 1.804 / 1.709 µs |
| 8,192 | 2.2 MB | 4,384 | 4,405 | 0.535 / 0.538 µs |
| 32,768 | 8.9 MB | 6,531 | 7,209 | **0.199 / 0.220 µs** |

작은 `k` 구역은 실행 간 차이가 크지만(k=8 이 4,739 vs 3,784) 큰 `k` 에서는 거의 같다(2.2 MB: 4,384 vs 4,405).
이 사실 자체가 아래 모델의 근거다 — **바닥값은 재현되고, 부피 항은 재현되지 않는다**.

`k=32` 가 그 구역에서 가장 비싼 것(7,569 / 7,862 µs)은 **첫 실질 flush** 의 값이다(새 파일 · 직전에 쌓은 dirty 가
없는 상태 → 커널이 한 번에 밀어내는 첫 경로). 그 뒤로는 오히려 싸진다.

### 2-1. 모델: `c(k) ≈ c_floor` (+ 상한이 있는 부피 항)

| 항목 | run A | run B | 읽는 법 |
| --- | --- | --- | --- |
| **바닥값** `c_floor`(k≥8 최소값의 중앙값) | **4,383.5 µs** | **4,216.1 µs** | 호출당 **배리어 고정세** |
| 바닥값이 가장 큰 호출에서 차지하는 몫 | **67.1 %** | **58.5 %** | **8.9 MB 조차 절반 이상이 부피 무관** |
| 부피 항 상한(큰 두 점의 현) | 0.330 µs/KB | 0.431 µs/KB | 2.4–3.1 GB/s — **민감도로만** 쓴다 |
| **유휴 호출**(이 파일은 깨끗, 쓸 것 없음) | 4,118.6 µs | 4,013.1 µs | **“쓸 게 없으면 공짜”가 아니다 — 호출당 같은 값** |
| 이웃 파일의 dirty 64 MB 를 더럽힌 상태 | **0.99×** | **1.02×** | 이 호출은 **남의 바이트를 지불하지 않는다** |

**선형 적합(`a + b·k`)은 쓰지 않는다**: `volume_term_observable` 판정이 실행마다 **뒤집혔다**(A 미관측 / B 관측)
— 큰 두 점의 차이가 잡음 띠와 같은 크기이기 때문이다. 식별되지 않는 항을 점추정으로 쓰면 서사(“부피가 비용을
만든다”)가 처방을 잘못 이끈다. 그래서 **바닥값 + 상한**으로 적고, 부피 항은 §3 의 민감도 열로만 본다.
(계기 계약 시험 `test_the_floor_dominates_even_the_largest_call` 이 “8.9 MB 조차 바닥값 점유율 ≥ 50 %”를,
`test_recorded_runs...` 계열이 판정 뒤집힘을 고정한다.)

## 3. 일정 셋 × 창 크기 — 커밋당 상각은 **주기만 정하면 끝난다**

주기 T초마다 1회면 창은 T초의 이력이고, 커밋당 상각 = `c_floor/(605·T)` 다(run A 바닥값 4,383.5 µs 기준 ·
run B 로 계산해도 상각은 7.0831 / 0.8112 / 0.2305 / 0.1260 / 0.1163 µs 로 같은 결론이다).

| 주기 T | 창(커밋 · 바이트) | 호출값 | **커밋당 상각** | 예산 대비 | 8시간 호출 수 |
| --- | --- | --- | --- | --- | --- |
| 1 s | 605 · 164 KB | 4,383.5 µs | **7.2455 µs** | 0.44 % | 28,800 |
| 10 s | 6,050 · 1.6 MB | 4,383.5 | **0.7245 µs** | 0.044 % | 2,880 |
| 60 s | 36,300 · 9.8 MB | 4,383.5 | **0.1208 µs** | 0.0073 % | 480 |
| 600 s | 363,000 · 98 MB | 4,383.5 | **0.0121 µs** | 0.0007 % | 48 |
| 3,600 s | 2,178,000 · 590 MB | 4,383.5 | **0.002 µs** | 0.0001 % | 8 |

민감도(부피 항을 0.5 GB/s 로 **가정**했을 때, 이 기기에서 관측된 가장 느린 8.9 MB 호출이 함의하는 값):
T=1 s **7.79** · 10 s **1.27** · 60 s **0.66** · 600 s **0.55** µs/커밋 — 즉 **가장 나쁜 가정에서도 예산의 0.47 %** 다.

**이 표가 말하는 것**: 체크포인트(저널 회전)와 셧다운은 이 산술의 두 극단이다 — 창이 각각 “회전 간격”과
“프로세스 수명”이다. 그리고 **비용은 결정을 못 가른다**: T=10 s 만 되어도 상각이 예산의 0.05 % 다.
가르는 것은 §4 다.

## 4. 간섭 — “핫패스 밖”은 가정이 아니라 재야 할 주장이었다

커밋당 예산 1,653 µs 페이스로 **605 ops/s** 를 맞춰 도는 쓰기 위에 배경 스레드가 `media` 를 부른다.
기준선을 **매 라운드** 끼워 짝지어 비교한다(첫 시도의 순차 설계는 실패했다 — §6 의 셋째 줄).

| 팔 | run A 중앙 Δ | run B 중앙 Δ | 최악 라운드 | >100 ms 밀림 | 밀림∩호출 | 배경 호출 최대 | 호출 수(10블록) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **기준선**(media 없음) | 0 % (604.5 ops/s) | 0 % (604.5) | 0 % | **0 / 0** | — | — | 0 |
| 같은 파일 · 200 ms | **−27.39 %** | −2.21 % | −78.18 / −34.87 % | **8 / 5** | **8/8 · 5/5** | 3.21 s / 0.13 s | 50 / 50 |
| 같은 파일 · **1,000 ms** | **−0.44 %** | **−0.43 %** | −18.51 / −35.10 % | 0 / 2 | — / 2-2 | 2.79 s / 3.20 s | 12 / 13 |
| **다른 파일** · 200 ms | −4.57 % | −1.78 % | −77.69 / −55.91 % | **6 / 6** | 6/6 · 6/6 | 3.24 s / 1.07 s | 50 / 50 |

읽어야 할 것 넷:

1. **밀림은 배경 호출과 100 % 겹친다** — 두 실행의 모든 >100 ms 밀림(8+5+6+6+2건)이 **진행 중인 `media` 호출
   구간 안**에서 일어났고, 기준선 10블록에는 밀림이 **한 건도** 없다. 평균이 아니라 **구간**으로 물었기 때문에
   보이는 것이다(밀림은 평균을 거의 안 올리고 꼬리만 키운다).
2. **다른 파일이어도 멈춘다**(다른 파일 200 ms 팔: 중앙 −1.8~−4.6 %, 밀림 6/6 겹침, 최대 3.2 s). 즉 **단위를
   “대화별”로 좁히는 것만으로는 다른 대화를 보호하지 못한다** — 이 호출은 장치 수준 배리어다.
   반대로 **호출의 값 자체는 이 파일 범위**다(§2-1: 이웃 dirty 0.99–1.02×).
3. **드물게 부르면 중앙 비용은 사라지지만(1,000 ms 팔: −0.43 %/−0.44 %, 두 실행 일치) 스톨은 남는다**
   (run B 1,000 ms: 밀림 2건 · 배경 호출 최대 3.20 s). **빈도는 주기로 줄일 수 있고, 스톨 자체는 못 줄인다.**
4. **유휴 창에서는 아무도 안 멈춘다**: 이 파일이 깨끗할 때 호출은 4.0–4.1 ms(§2-1)이고 — 그 측정은 soak 이
   같은 디스크에 **계속 쓰는 동안** 얻은 값이다. 즉 스톨의 원인은 (측정이 지지하는 가설) **자기 파일의 dirty
   페이지를 뒤쫓는 배리어와 그 파일에 계속 append 하는 쓰는 쪽의 경합**이다.

### 5-1. D-F3-2 에 대한 답 — **“대화별 옵트인”이되, 보호 장치는 단위가 아니라 정지 감지다**

- **단위: 대화별 옵트인**(권고). 전역 주기는 비용이 테넌트 수에 곱해지고(P1), 다른 대화의 `media` 가 이 대화의
  쓰기를 멈추므로(§4-2) “전역이면 장치가 한가할 때 알아서 하겠지”라는 기대도 성립하지 않는다.
- **결정적인 조건: `T_max` 상한이 있는 정지 감지(deferred-until-quiet).** 조용한 창에서의 호출은 4.0–4.1 ms 이고
  멈추는 쓰는 쪽이 없다(§4-4). 조용한 창이 상한 안에 안 오면 **강행하되 스톨을 관측에 남긴다** — 창을 줄이려고
  조용히 스톨을 키우지 않는다.
- **체크포인트는 단독으로는 안 된다**(P3): 창이 회전 간격인데 핫한 대화는 회전하지 않는다. 체크포인트/셧다운은
  “추가 기회”(조용한 창의 한 종류)로만 쓴다.
- **`media` 를 요구해도 기본 등급은 `cache` 그대로**(D-F3-1 권고와 독립) — 켜지 않은 대화의 동작은 오늘과 같다.

## 7. 한계(먼저 적는다)

1. **크래시 유실은 실측할 수 없다**(전원 손실 필요) — 창은 규칙으로 정의했고 시험으로 간접 검증한다.
2. **스톨은 꼬리가 두껍다** — 10라운드 × 2실행에서 중앙 델타가 −27 % vs −2 % 로 흔들린다(같은 200 ms 팔).
   그래서 이 문서는 **중앙값과 밀림 건수·최대치를 함께** 적고, “몇 % 느려진다”를 한 수로 말하지 않는다.
3. **기준선도 공짜가 아니다** — 두 실행 모두 604.5 ops/s 로 예산을 정확히 지켰지만, 최대 gap 이 5.8–6.3 ms 인
   순간이 있었다(외부 부하). 그래서 밀림은 **>100 ms** 를 문턱으로 셌다.
4. **`T_max` 의 값은 이 문서가 정하지 않는다** — 창과 스톨의 교환은 오너의 위험 선택이다(권고: 60 s = 상각 0.12 µs).
5. 스톨의 **기제 설명**(자기 파일 dirty 를 뒤쫓는 배리어)은 §2-1 유휴 호출과 §4 의 상관이 함께 지지하는
   **가설**이다 — 배리어의 커널 내부를 직접 관측한 것은 아니다.
6. “미디어 보장” 자체는 플랫폼 **문서** 근거다(이 실측이 증명한 것은 비용과 간섭이다).
