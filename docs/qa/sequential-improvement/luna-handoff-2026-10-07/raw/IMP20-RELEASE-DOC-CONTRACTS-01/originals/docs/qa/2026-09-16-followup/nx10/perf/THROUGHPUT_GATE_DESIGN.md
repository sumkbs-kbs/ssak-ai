## 1. 먼저 밝힌 것: **벽시계 처리량 단독으로는 게이트가 될 수 없다**(실측)

오늘 돌고 있는 4차 실행(8시간 중 5시간)의 30분 블록을 실측했다:

| 축 | 첫 25% → 끝 25% | 판정 |
| --- | --- | --- |
| 벽시계 `ops/s` | 692 → 508 = **−26.5%** | 요구된 임계(27%)와 사실상 같은 값 |
| 효율 `ops/CPU초` | 779.9 → 740.6 = **−5.0%** | 허용 15% 안 |
| 이용률 `CPU초/벽초` | 0.887 → 0.686 = −22.6% | 기계가 바빴다(오늘 이 기계에서 게이트·리허설·프로브를 돌렸다) |

즉 **벽시계만 보는 게이트는 건강한 실행을 정확히 27% 지점에서 빨갛게 만든다.** 반대로 벽시계를 버리면
“덜 돌아간 실행”을 놓친다. 그래서 이 축은 단일 숫자가 아니라 **정체식으로 분해한 세 숫자**로 판정한다:

```
벽시계 처리량 = 효율(ops/CPU초) × 이용률(CPU초/벽초)
```

- **효율** = “한 일당 비용이 늘었나” → **제품 축**(기계 부하에 거의 흔들리지 않는다: 분모가 자기 CPU 시간)
- **벽시계** = “운영자가 겪는 것” → **서비스 축**
- **이용률** = “덜 돌았나(경합·대기)” → **진단 축**

세 비율의 곱이 벽시계 비율과 맞는지도 리포트에 남긴다(`throughput_identity_gap`).

> 왜 이 분해가 필요한가 — 같은 “27% 느려짐”이 세 가지 다른 사건일 수 있다:
> ① 코드가 느려졌다(효율↓) ② 기계가 바빴다(이용률↓, 효율 불변) ③ 제품이 **대기**를 늘렸다(I/O·lock·fsync;
> 이용률↓인데 **호스트는 조용**하다). 셋은 처방이 완전히 다르다(수정 / 재실행 / 수정).

## 2. 판정 규칙

입력은 하네스가 50 반복마다 남기는 표본이다(SC6 배치가 이미 `sample_ops`·`sample_times_s` 를 남긴다):

| 표본 | 의미 | 이 배치가 추가 |
| --- | --- | --- |
| `sample_ops[i]` | 누적 반복 수 | (SC6 에서 있음) |
| `sample_times_s[i]` | 실행 경과 초 | (SC6 에서 있음) |
| `sample_cpu_s[i]` | 누적 프로세스 CPU 초(`time.process_time()`) | **추가** |
| `sample_load1[i]` | 호스트 부하(`os.getloadavg()[0]`, 못 읽으면 −1) | **추가** |

**블록**: 표본 간 구간에서 `벽시계=Δops/Δt` · `효율=Δops/ΔCPU` · `이용률=ΔCPU/Δt` 를 내고,
`max(5분, 지속×2%)` 창(8시간이면 9.6분 → 약 50블록)의 **중앙값**으로 접는다.
**워밍업 제외**: SC-6 의 창(`max(5분, 지속×5%)`)을 그대로 쓴다 — 시작 비용·JIT·할당자·페이지 캐시가
차오르는 구간은 회귀 판정의 재료가 아니다.

**비교**: 워밍업 창 밖 블록을 사분위로 나눠 **첫 분기 중앙값 → 끝 분기 중앙값**의 비율을 낸다
(분기 = 블록의 1/4, 최소 3블록). 블록-중앙값의 중앙값이라 60초 표본 잡음(CV 16.8%)이 √블록 수 만큼 줄어든다.

**판정**(허용 감소 `THROUGHPUT_MAX_DECLINE = 15%`):

| 조건 | 판정 | 근거 문장이 밝히는 것 |
| --- | --- | --- |
| 효율 비율 < 0.85 | **fail** | “**제품 회귀**: 일당 비용이 X% 늘었다” — 벽시계와 무관하게 잡는다 |
| 벽시계 < 0.85 · 효율 ≥ 0.95 · **부하 > 0.5** | **not_applicable** | “제품 회귀 아님 — 호스트가 바빴다. 조용한 기계에서 다시 재야 한다” |
| 벽시계 < 0.85 · 효율 ≥ 0.95 · **부하 낮음** | **fail** | “**서비스 회귀**: 일이 줄어든 게 아니라 **대기가 늘었다**” |
| 벽시계 < 0.85 · **부하 미상** | **not_applicable** | “부하 계기를 못 읽어 귀속 불가 — 재실행 필요” |
| 그 밖 | pass | 두 숫자(실측·허용)를 함께 든다 |

**`not_applicable` 은 통과가 아니다**(SC-6 규칙). 짧은 실행에서만 면제한다: 실행이 그 축의
최소 길이(처리량 2시간 · RSS 창의 2배)보다 짧으면 면제 — 그 외에는 통과로 취급하지 않고 재실행을 요구한다
(`criteria_gate`). 이 문이 없으면 **환경 변수 한 줄로 게이트를 비울 수 있다**(스모그에서 실제로 드러났다:
60초 실행이 두 축 다 `not_applicable` 인데 시나리오 `pass = True` 였다).

**적용 하한**: 2시간 미만이면 판정하지 않는다(`THROUGHPUT_MIN_RUN_S`) — 60초 리허설은 시작 비용이 지배한다.

## 3. 임계 보정(모두 실측)

| 무엇 | 실측값 | 임계 결정 |
| --- | --- | --- |
| 잡아야 하는 회귀 | 27%(지시) | 허용 **15%** → 여유 **12%p** |
| 건강한 실행의 효율 감소 | 4차 **5.0%** | 15% 안(여유 10%p) |
| 건강한 실행의 벽시계 감소 | 4차 26.5%(경합) · 3차 **−6.1%**(조용) | 벽시계 단독 판정 금지의 근거 |
| 60초 표본 잡음 | CV **16.8%** | 두 점 비교 금지 → 블록 중앙값 |
| 10분 블록 편차 | 중앙 8.4% · 최대 **29.6%** | 블록 하한 5분 + 사분위 중앙값 |
| 30분 블록 편차 | 중앙 6.0% · 최대 30.1% | 8시간 기준 9.6분 블록 ≈ 이 수준 |
| 호스트 부하 판별 | 4차의 이용률 −22.6% 가 경합 | `load1/코어 > 0.5` 면 제품 탓으로 단정하지 않음 |

> **집계 평균은 이 축을 대신하지 못한다**(리포트에 시계열이 없던 이유이기도 하다): 누수 실행
> `soak-28800-fail001.json` 은 `completed_ops 70,430 / 28,800s = **2.4 ops/s**` 인데, 4차 실행은
> **약 562 ops/s** 다 — **230배** 차이다. 그 실행을 우리는 “RSS 누수”로 판정했고, **처리량 재앙은
> 어느 게이트도 말하지 않았다**. 시계열이 없으면 이런 것이 통째로 보이지 않는다.

## 6. 남는 한계(먼저 적는다)

1. **이 축은 단일 기계 위에서만 뜻이 있다.** 부하 귀속은 `load1/코어` 라는 거친 프록시에 기대고,
   “같은 코어를 두고 경합하는 다른 에이전트”와 “I/O 대기”를 완전히 가르지는 못한다 — 그래서 미상·경합은
   **통과가 아니라 재실행**으로 처리한다.
2. **CPU 표본은 `time.process_time()`** 이다. macOS 에서 자식 프로세스·스레드의 CPU 는 포함되지만
   시스템 콜에서의 대기는 CPU 로 세지 않으므로, “대기 증가”는 이용률 하락으로만 보인다(의도).
3. **감사(attribution)는 하지 않는다**: 회귀를 잡으면 *어느 호출이 느려졌는지*는 별도 조사다(오늘 RSS 의
   “출처 추적”을 그렇게 했듯이). 이 게이트는 **잡고, 분해하고, 처방을 가르는** 데까지다.
4. **journal 바이트 프록시**: 감시기(`soak_watch.py`)의 처리량은 여전히 바이트 추정이다. 하네스가 남기는
   `sample_ops` 가 정본이고, 감시기는 조기 경보용이다.
5. **6만 초 이상의 실행**에서는 블록이 2% 로 커져(>20분) 분기 해상도가 떨어진다 — 상한을 두는 결정은 오너 몫.

## 9. 귀속 사다리 — “느려졌다” 다음의 질문: **어느 호출이** 느려졌나

오너 지시(2026-09-17): *“처리량 회귀가 잡혔을 때 어느 호출이 느려졌는지 자동으로 좁혀 주는 귀속 사다리를
설계하고 계약 시험으로 고정해줘.”*

게이트(§1~§4)는 **잡고·분해하고·처방을 가른다**. 남는 질문은 항상 같다: 일당 비용이 늘었다면 **어느 호출**
때문인가. 사다리는 그 질문을 다섯 칸으로 내려간다 — 그리고 **아는 만큼만 말한다**.

### 9-1. 국면(phase)과 쪼개기

한 반복은 세 국면을 순서대로 지난다(`SOAK_PHASES`):

| 국면 | 반복당 호출 | 실측 단가(60초 실행 · 프로브) |
| --- | --- | --- |
| `task.create` | `create_task` 1회 | **500 µs** |
| `task.transition` | `transition` 2회(pending→running→done) | **980 → 1,000 µs**(가장 비싼 국면) |
| `conversation.append` | `append` 1회(저널 1줄 + view 재작성 + `tail`) | **760 µs** |

하네스가 국면 경계에서 `time.process_time()` 을 적립한다(반복당 3회). **반복 끝에서 시계를 청구 없이
리셋**하므로 루프 자체·표본 수집·할당자·GC 는 어느 국면에도 안 붙고, 그만큼이 자연히 **잔차**가 된다.

쪼갠 합이 총량과 같아야 하므로(정체식) 총량은 **프로세스 전체 CPU 표본**에서 따로 잰다. 국면 합을 총량으로
쓰면 잔차가 정의상 0 이 되어 “계측 밖”이라는 판정이 **영영 안 난다** — 실제로 첫 구현이 그랬고, 계약 시험
⑯ 이 그 구멍을 겨눈다.

### 9-2. 다섯 칸

| 칸 | 조건 | 말하는 것 |
| --- | --- | --- |
| `not_applicable` | 게이트가 빨갭지 않거나 실행 < 2시간 | **돌지 않는다** — 귀속은 빨간 판정의 *설명*이지 별도 판정이 아니다 |
| `insufficient` | 총 증가 < 첫 분기 단가의 2%(잡음) · 또는 계열/블록 부족 | **아무도 지목하지 않는다** — 없는 범인을 만들지 않는다(다음 칸: 재실행·노브) |
| `outside_phases` | 잔차 > 총 증가의 50% | 할당자·GC·인터프리터·루프 자체 → **프로세스 전체 프로파일**(cProfile/py-spy) |
| `phase` | 한 국면이 증가분의 ≥ 50% | **그 이름을 지목** + 몫 + 다음 칸(그 경로의 하위 단계) |
| `spread` | 지배 국면 없음 · 잔차 작음 | 고르게 늘었다 → **공통 경로**(직렬화·할당·로그) |

빨라진 국면은 **음수 기여**로 남겨 지목하지 않는다(⑱). 임계는 `ATTRIBUTION_DOMINANCE=0.5` ·
`ATTRIBUTION_MIN_DELTA_RATIO=0.02` · `ATTRIBUTION_OUTSIDE_GAP_RATIO=0.5` 이고, 스냅샷 간격은
`NX10_ATTRIBUTION_SAMPLE_EVERY`(기본 500 반복)로 통제한다 — 8시간·605 ops/s 에서 약 3.5만 표본
(국면 3개 × 3.5만 ≈ 1.1 MB)이고, 처리량 2.4 ops/s 인 누수 실행에서는 138 표본으로 줄어든다.

### 9-3. 추정량이 보는 것(숨기지 않는다)

분기 중앙값을 쓰므로 선형 궤적에서 측정값은 궤적의 **12.5% / 87.5%** 지점에 앉는다 — 즉 **주입 증가분의
약 72~75%** 를 본다(워밍업 창이 앞을 잘라 72%). 시험 ⑭ 가 그 성질을 기대값으로 밝혀 둔다. 그래서 사다리의
숫자는 “얼마나 느려졌나”의 상한이 아니라 **어느 국면인가**를 가리는 데 쓴다(비율·몫이 판단의 재료다).

### 9-4. 배선 실측(프로브) — 계약 시험 밖의 것을 본다

`perf/probe_ladder_end_to_end.py` → `perf/probe-ladder-output.json`(실제 하네스 실행 3회 · 60초):

| 실행 | 조건 | 결과 |
| --- | --- | --- |
| A | 상수 그대로 | 게이트 `not_applicable`(60초는 5분 블록을 못 채운다) · 사다리 미실행 · 국면 스냅샷 **32개 적립** |
| B | 프로브 노브(블록 1초·워밍업 3초·최소 30초) | 게이트가 **판정을 낸다**(블록 48개) → 벽시계 −5.1% · 효율 −2.7% → `pass` — 경합이 아니라고 말한다 |
| C | 같은 노브 + 게이트 인위 빨강 | 사다리가 **실제 계열을 쪼갠다**: 블록 46개 · 총 단가 2,240→2,280 µs/반복 · 국면 create 500 · transition 980→1,000 · append 760 → **Σ 국면 = 2,240 = 총량 first** (정체식이 실측에서도 성립) · 판정은 `insufficient`(+1.8% 는 잡음) |

C 가 보여 주는 것은 **정확한 귀속이 아니라 계열의 풍부함**이다: 8시간을 쓰기 전에 “실제 하네스 계열이
국면 쪼개기를 감당하는가”(블록 수·단가 채움)를 확인한다. 배선이 끊겼다면 프로브가 즉시 빨개진다.

### 9-5. 남는 한계

1. **`phase` 칸을 실측 데이터로 태운 적은 아직 없다** — 실측 60초 실행의 단가 증가가 잡음 수준이라
   합성 픽스처로만 증명됐다. 그 칸은 **다음 8시간 soak** 이 처음 태운다(회귀가 없다면 `not_applicable` 로 끝난다).
2. **국면은 경계까지만 본다.** 한 국면 안의 어느 하위 단계가 느려졌는지는 다음 칸이다(⑯ 의 `next_step` 이
   그걸 말한다). 이 사다리는 **자동으로 사람을 한 칸 좁혀 놓는** 데까지다.
3. **국면 목록이 하드코딩**되어 있다(3개). 새 작업이 soak 루프에 들어오면 그 비용은 “국면 밖”으로 간다 —
   회귀처럼 보일 수 있으므로 `attribution_phases` 를 리포트에서 확인해야 한다.
4. **`process_time()` 기반**이라 대기(블로킹 I/O)는 국면 단가에 안 들어간다 — 대기는 게이트의 **이용률** 축이 잡는다.

## 10. 사다리의 다음 칸 — 지목된 국면 **안**의 하위 단계

오너 지시(2026-09-17): *“지목된 국면 안의 하위 단계(저널 append · view 재작성 · tail 같은)까지 자동으로
좁히는 사다리 다음 칸을 설계하고 계약 시험으로 고정해줘.”*

국면(§9)까지 좁혀지면 다음 질문은 항상 같다: `conversation.append` 안에서 **저널 한 줄 쓰기 · view
재작성 · tail 중 무엇**이 늘었나. 그 단계들은 **제품 코드 안**(`src/`)에 있어 경계 타이머를 심을 수 없다
(그리고 그 파일들은 지문 대상이다 — 잴 때마다 제품을 고칠 수는 없다). 그래서 하네스가 **창(window) 단위로
`cProfile` 을 걸어 파이썬 수준 귀속**을 얻는다.

### 10-1. 계측 설계 — 판정을 오염시키지 않는 세 장치

| 장치 | 왜 | 실측 근거 |
| --- | --- | --- |
| **창 = 국면 하나**(국면을 돌려 가며) | “그 국면 안의 함수 순위”를 얻으려면 창마다 국면이 정해져야 한다 | 창 40개가 `create 14 · transition 13 · append 13` 로 고르게 돌아간다 |
| **계측한 반복은 판정 계열에서 제외** | 프로파일러가 국면을 1.5배로 부풀린다 — 넣으면 “느려졌다”가 측정기 때문이 될 수 있다 | `deep_overhead_ratio` **1.50** · 계열 분모에서 계측분을 뺀다(`attribution_measured_ops`) |
| **오버헤드·계측기 몫을 밝힌다** | 측정기가 만든 몫을 숨기면 잔차가 거짓말이 된다 | `deep_instrument_us_per_op` · `deep_overhead_ratio` · 음수 잔차엔 `deep_residual_note` |

표본률은 기본 **1/200 반복**, 창 크기 25 호출, 창 상한 40(총 1,000 호출 = 8시간·605 ops/s 에서 측정
계열의 **0.006%**). 껐다가 켤 수 있다(`NX10_DEEP_PROFILE=0`, `NX10_DEEP_SAMPLE_EVERY`) — 이 칸은 **설명용**이라
꺼도 통과/실패 판정은 약해지지 않고, 대신 “왜 느린지”를 말할 수 없다고 리포트가 밝힌다.

### 10-2. 판정 — 아는 만큼만

| 칸 | 조건 | 말하는 것 |
| --- | --- | --- |
| `not_applicable` | 앞칸이 국면을 지목하지 않았거나 실행 < 2시간이거나 계측을 껐다 | 함수 순위는 **지목된 국면에만** 묻는다 |
| `insufficient` | 창 < 3개 또는 통계 비었음 | 아무도 지목하지 않는다(노브·길이를 바꿔 다시) |
| `function` | 한 함수 ≥ 국면 안 파이썬 시간의 50% | **이름 지목** + 몫 + 다음 칸 |
| `spread_within_phase` | 지배 함수 없음 · 잔차 작음 | 그 국면 안에서 더 쪼갤 근거가 없다 → 일감량·구조를 본다 |
| `outside_functions` | 잔차(계측기 몫을 뺀 뒤 남는 것) > 국면 단가의 50% | 파이썬 프로파일러가 못 보는 곳 → syscall·쓰기량·C 스택 도구 |

### 10-3. 실측이 곧바로 답을 냈다 — `conversation.append` 는 **fsync** 다

프로브 D 실행(60초 · 실제 하네스 · 창 13개):

| 국면 | 파이썬이 본 단가 | 상위 함수(자기 시간) | 판정 |
| --- | --- | --- | --- |
| `task.create` | 604 µs/반복 | `builtins.next` 587 · sqlite `commit` 555 · `execute` 203 | 세 국면 중 가장 싸다 |
| `task.transition` | 1,085 µs/반복 | `builtins.next` 472 · sqlite `execute` 398 · `commit` 305 | sqlite 쓰기 경로가 지배 |
| `conversation.append` | 1,223 µs/반복 | **`posix.fsync` 847(69%)** · `posix.replace` 98 · `_io.open` 80 | **`function` — 이름을 지목했다** |

즉 “저널 line 쓰기 · view 재작성 · tail” 중 지배 항은 **`fsync`(내구성 flush)** 이고, view 재작성·tail 은
그 뒤다. 이 칸이 노린 것이 정확히 이것이다 — 국면 이름(`conversation.append`)만으로는 “JSON 이 느린가?”로
읽히지만, 실제로는 **디스크 flush 비용**이다(그래서 처방이 “직렬화 줄이기”가 아니라 “flush 정책·배치”가 된다).

### 10-4. 남는 한계

1. **`function` 칸도 실측에서 나왔지만, 이는 60초 실행·프로버 노브의 결과다.** 8시간 실행의 국면 지목 →
   함수 지목 연쇄는 아직 실제로 태운 적이 없다(회귀가 없으면 두 칸 다 `not_applicable` 로 끝난다).
2. **C 확장은 자기 시간이 부풀려진다**: cProfile 은 호출마다 계측을 끼워 넣으므로 순위는 신뢰하되
   **절대값은 오버헤드를 감안해** 읽어야 한다(그래서 `deep_overhead_ratio` 를 항상 싣는다).
3. **창 경계는 호출 단위**다: 창이 반복 중간에 닫히면 그 반복의 남은 호출은 계측도 계열도 안 들어간다
   (창당 최대 1회분 · 전체에서 무시할 수준이나, 정확히 말해 둔다).
4. **프로파일러는 파이썬만 본다** — 커널·C 몫은 잔차로만 보인다(§10-2 의 `outside_functions`).
5. **셋째, 국면 함수 순위의 *몫* 은 실행마다 흔들린다** — 실측: 같은 일감(200 반복)을 세 번 재니
   `posix.fsync` 자기 시간이 **1,930 µs(54.9%) · 27.5 µs(2.7%) · 27.9 µs(2.6%)** 로 70배 차이났다(디스크가
   더러운 상태냐에 달려 있다 — `fsync` 는 커널 대기라 상태 의존적이다). 그래서 **첫 회차 프로브의
   “fsync 847 µs = 69%” 는 틀린 값이 아니라 *그 때의 디스크* 값**이고, 다음 프로브에서는 405 µs = 33% 로
   나와 판정이 `function` 에서 `spread_within_phase` 로 바뀌었다. 진단할 때는 **순위와 호출 횟수**를 읽고
   몫은 “그 순간의 크기”로 읽어야 한다 — 이 흔들림은 §11 의 **빈도 축**이 결정적인 이유이기도 하다.

## 11. 사다리의 **네 번째 칸** — 지목된 함수를 **누가·얼마나 자주** 부르는가

오너 지시(2026-09-17): *“지목된 함수가 어느 호출 경로에서 얼마나 자주 불리는지까지 자동으로 좁히는 사다리
네 번째 칸을 설계하고 계약 시험으로 고정해줘.”*

### 11-1. 왜 둘(경로·빈도)을 나눠 내는가

앞칸이 “`posix.fsync` 다”까지 말한 뒤 남는 질문은 둘이다. 그리고 **그 둘이 처방을 가른다**:

| 답 | 처방 |
| --- | --- |
| 반복당 **1회** (빈도) | 횟수는 이미 최소다 → **그 호출 자체를 싸게** 만든다(정책·배치·비동기화) |
| 반복당 **여러 번** (빈도) | 한 번으로 줄일 여지가 있다 → **호출을 합친다**(중복 제거·일괄 처리) |
| 한 경로가 지배 (경로) | 그 경로를 고친다 |
| 여러 경로가 부른다 (경로) | 부르는 곳을 고치는 대신 **그 함수 자체**를 싸게 만든다 |

같은 함수·같은 시간이라도 다른 수술이므로, 한 숫자로 눌러 담지 않고 **경로 판정**(`path`)과 **빈도
분류**(`frequency`)를 별도 필드로 낸다. 빈도는 판정을 흔들지 않는다(시험 ㊶).

### 11-2. 자료는 이미 있다 — 다만 `getstats()` 의 6번째 칸이 함정이다

`cProfile` 통계는 **호출자 표**를 이미 만들고 있다(새 계측 비용 0). 그런데 그걸 꺼내는 문이 직관과 다르다:

> `Profile.getstats()` 가 돌려주는 튜플의 **6번째 칸은 callees(내가 부른 것)** 이고 호출자가 아니다.
> 내장 함수는 거기서 `None` 을 준다 — 그걸 호출자로 읽은 첫 구현은 **바로 `None` 을 만났다**(프로브가 실측).
> `pstats.Stats(profile).stats` 가 그 callee 목록을 뒤집어 **호출자 표**를 만들어 준다(`print_callers` 가
> 쓰는 그 자료다). 튜플 순서도 다르다: raw 는 `(code, nc, cc, ns, tt, ct)` · pstats 는 `(cc, nc, tt, ct, callers)`.
> 주의: `Stats(profile)` 는 `profile.stats` 를 **비운다** — 같은 프로파일러로 두 번 부르면 두 번째는 빈다.

**교체가 측정을 바꾸지 않았는지 실측으로 확인했다**: 같은 프로파일에서 `pstats.tt` 와 `raw[4]`(inlinetime),
`pstats.ct` 와 `raw[3]`(totaltime)이 **소수점까지 일치**했다(상위 6개 프레임 전부). 즉 이번 교체는 순수하게
“호출자 표를 얻기 위한 통로 교체”이고 숫자를 건드리지 않았다.

### 11-3. 판정

| `path_criterion` | 조건 | 말하는 것 |
| --- | --- | --- |
| `not_applicable` | 앞칸이 함수를 지목하지 않았다 · 실행 < 2시간 · 계측 꺼짐 | 돌지 않는다(경로는 **지목된 함수에만** 묻는다) |
| `insufficient` | 창 < 3 · 호출 0 · 호출자 표가 비었거나 **불완전** | 지목하지 않는다 · 노브/도구 안내 |
| `path` | 한 호출자 ≥ `PATH_MIN_CALLER_SHARE`(0.5) | **그 경로다** — 이름·몫·사슬 |
| `multi_path` | 여러 곳 · 지배자 없음 | 부르는 곳을 고칠 것이 없다 → **함수 자체**를 싸게 |

세 가지를 숨기지 않는다: ① **하네스가 직접 부르면 “국면 진입점”**이라 밝힌다(계측기를 범인으로 만들지
않으면서 “제품 쪽에 고칠 곳이 없다”는 사실을 전한다) ② 몫의 분모는 **그 함수 자신의 호출 수**다(보관한
상위 호출자만 더하면 트리밍된 나머지를 숨기며 몫을 부풀린다) ③ 사슬을 걸을 때 계측기 프레임은 건너뛰고
**건너뛴 수를 밝힌다**.

임계: 호출자 몫 0.5 · 함수당 싣는 호출자 5곳(리포트 상한) · 사슬 깊이 4 · 빈도 경계 1.5회/반복.

### 11-4. 실측이 답을 냈다(프로브 E · 실제 하네스 · 창 13개)

```
판정: path · 함수 posix.fsync · 반복당 1.00회 (at_most_once_per_iteration)
호출자: conversation_journal.py:_fsync_fd   (몫 1.00 · 호출 325회)
사슬: posix.fsync ← conversation_journal.py:_fsync_fd ← conversation_journal.py:_append_bytes
      ← conversation_journal.py:append ← conversation_store.py:_commit_event
다음 칸: `_fsync_fd` 경로를 본다 — 반복당 1.00회 — 횟수가 아니라 그 호출 자체의 비용이 문제다
```

즉 “`append` 안의 `fsync`”(셋째 칸)가 **“저널의 `_fsync_fd`, 반복당 정확히 1회, `_commit_event` 에서
시작하는 사슬”**(넷째 칸)이 된다. **빈도 1.00 이 이 칸의 핵심 산출**이다: 반복당 한 번이면 코얼레싱으로
줄일 것이 없고(`fsync` 는 한 번의 저널 커밋에 한 번이면 최소다), 처방은 **그 한 번을 싸게 만드는 정책·배치**다.

### 11-5. 짚고 간 계약 하나 — 창은 **샘플 주기의 배수**에서만 열린다

`take()` 는 `index % DEEP_SAMPLE_EVERY == 0` 인 반복에서만 창을 연다. 그래서 창 상한 40개를 다 쓰려면
반복 인덱스가 `40 × 200` 이상 흘러야 한다 — 1,200 반복짜리 시험 구동으로는 열림 기회가 5번뿐이라 국면당
창이 2개로 끝나고 넷째 칸이 `insufficient` 로 **죽는다**(시험을 쓰다 실측으로 밟았다: “창 2개 · 계측 반복 50”).
실제 8시간 실행(반복 수천만)과 60초 프로브(기회 180번)는 무관하다. 시험 구동은 20,000 반복으로 돌린다.

### 11-6. 남는 한계

1. **`path` 칸도 60초 프로버 노브에서 나온 결과다** — 앞 두 칸처럼 8시간 연쇄는 아직 태운 적이 없다.
2. **셋째 칸의 몫이 흔들리면 이 칸도 안 돈다**(앞칸이 `function` 일 때만 돈다 · §10-4 ⑤). 흔들림은
   *빈도* 쪽이 안정적이라는 뜻이므로, 이 칸의 값은 **빈도와 호출자 표**를 먼저 읽는 것이 맞다.
3. **호출자가 C 쪽이면 답하지 못한다** — 그때는 `insufficient` 로 남고 다음 도구(syscall·trace)를 안내한다.
4. 호출자 표는 **창 안의 호출**만 센다(창 밖은 계측되지 않았다 — 국면 단가와 같은 표본이다).
