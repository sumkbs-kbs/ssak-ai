# flush 정책·배치 설계 — `conversation.append` 의 fsync 를 어떻게 다룰 것인가

오너 지시(2026-09-17): *“`conversation.append` 의 fsync 69% 를 근거로 flush 정책·배치 대안들을 동결 해제 뒤
지문에 반영할 수 있는 배치로 설계해줘.”* — 이 문서는 **동결 해제 뒤 바로 적용할 수 있는 배치**의 설계다.
배치 이름: **`FLUSH`**(스테이징 `nx10/fsync/`). 본실행은 **아직 하지 않았다**(동결 중 · `src/` 는 지문 대상).

**구성**: F1 = 배치 `FLUSH`(코드·시험·리허설 **준비 완료**) · F2 = 배치 `FLUSH2`(**신선도 계약 결정·구현·리허설
완료** — [fsync2/VIEW_FRESHNESS_CONTRACT.md](../fsync2/VIEW_FRESHNESS_CONTRACT.md) · §10-2) · F3 = 배치 `FLUSH3`
(설계만 · ADR-DAT-02 §2 개정이 **선행물** · D-F3). §10 이 “결정 뒤 어떻게 그 배치를 만드는가”이고,
§10-1 이 세 대안을 한 표에 놓고 고르게 한다.

---

## 0. 먼저 바로잡을 것 — “69%”는 그 때의 디스크 값이다

사다리 셋째·넷째 칸이 이 배치의 출발점이다(대장 §31·§32):

```
path: posix.fsync · 반복당 1.00회 (at_most_once_per_iteration)
호출자: conversation_journal.py:_fsync_fd   (몫 1.00)
사슬: posix.fsync ← _fsync_fd ← _append_bytes ← conversation_journal.py:append ← _store._commit_event
```

그런데 그 **몫**은 흔들린다. 같은 일감(200 반복)을 세 번 재니 `fsync` 자기 시간이 **1,930 µs(54.9%) ·
27.5 µs(2.7%) · 27.9 µs(2.6%)** 였다 — **70배** 차이다. 뒤이은 곡선 측정이 이유를 보여준다(§1):

| 페이지 캐시 더티 | 0 MB | 8 MB | 64 MB | 256 MB |
| --- | --- | --- | --- | --- |
| `fsync` 지연(중앙값) | **22.4 µs** | 341.3 µs | 352.0 µs | 289.3 µs |

즉 fsync 비용은 **“캐시가 더러운가”의 계단 함수**이고, 일감 크기(저널 271 B/append)와 무관하게 대략
**300~350 µs 의 고정세**가 붙는다. 따라서:

- **“append 를 가볍게 하면 fsync 가 싸진다”는 성립하지 않는다** — 직렬화·바이트를 줄여도 이 세금은 그대로다.
- 남는 지렛대는 둘뿐이다: ① **sync 를 덜 부른다**(정책 — 내구성 계약을 바꾼다) ② **fsync 주변을 덜 쓴다**
  (예산 — 계약을 안 바꾼다). 이 배치는 그 둘을 **다른 부품**으로 나눈다.

## 1. 증거 — 결정적 예산과 비용 곡선

도구: `nx10/fsync/probe_flush_path.py` · 출력 `probe-flush-output.json`(읽기 전용 아님 — 임시 루트에만 쓴다).

### 1-1. append 1회의 예산(deterministic — 디스크 상태와 무관)

| 항목 | 실측 | 비고 |
| --- | --- | --- |
| `os.fsync` | **1.000** | 내구성 계약(ADR-DAT-02 §2) |
| `os.open` / `os.close` | 5.000 / 5.000 | 저널 꼬리 3 × 2 + append 1 + view 1 |
| `os.pread` | 3.000 | **꼬리 창 3회** |
| **읽은 바이트** | **116,025 B (≈113 KiB)** | 같은 꼬리를 세 번 다시 읽는다 |
| `os.stat` / `os.fstat` | 11.000 / 3.000 | |
| `os.replace` | 1.000 | view 원자 교체 |
| **`tail()` 호출** | **3.000** | 그림 1 참조 |
| **view 재작성** | **1.000회 · payload 8,021 B** | 매 append 마다 |
| 저널 증가 | 271 B/append | |

**꼬리 읽기 3회의 출처**(소스 확인):

```
append()  ─┬─ _authoritative_record()        → journal.tail()   (seq/revision 판정)
           ├─ _reconcile_view_with_journal() → journal.tail()   (view 가 미커밋 tail 을 포함하는가)
           └─ _commit_event()                → journal.tail()   (미결 꼬리 검사)
                                             → journal.append() → self.tail()  (seq 부여)
```

네 지점이 **같은 flock 임계 구역 안**에 있고, 그 구역에서 이 프로세스가 쓰지 않는 한 꼬리는 변하지 않는다.

### 1-2. 플랫폼 능력(배치가 플랫폼별로 달라야 하는 이유)

`platform=darwin · os_fdatasync 있음=False · fcntl.F_FULLFSYNC 있음=True`. 즉 여기서 `os.fsync` 는
**미디어까지 내려간다는 보장이 아니다** — macOS 의 내구성 syscall 은 `F_FULLFSYNC` 다. 이 사실은 §4-3 의
“내구성이라는 말의 플랫폼별 의미” 결정으로 이어진다.

## 2. 세 부품으로 나눈다 — 위험·계약 영향별로

| 부품 | 무엇 | 계약 영향 | 지문 영향 | 상태 |
| --- | --- | --- | --- | --- |
| **F1** | 꼬리 읽기 **3회 → 1회**(+ 통계 최소화) | **없음** | 있음(`src/`) | **스테이징 완료 · 리허설 ALL PASS 16/16** |
| **F2** | **view 재작성 스로틀**(매 append → 필요할 때) | 읽기 표면의 신선도 | 있음 | 설계만(오너 결정 D-F2) |
| **F3** | **sync 정책**(`always`/`batched`/`fdatasync`) | **ADR §2 문장을 바꾼다** | 있음 | ADR 개정 초안 필요(오너 결정 D-F3) |

**나누는 이유**: F1 은 “같은 일을 더 적은 syscall 로”이고, F2·F3 은 “무엇을 보장할 것인가”를 바꾼다.
성격이 다른 결정을 한 배치에 묶으면, 내구성 논쟁이 **예산 절감까지 함께 멈춰 세운다**.

## 3. F1 — 안전·결정적(이 배치의 본체)

### 3-1. 계약

> 커밋 임계 구역(flock) 안에서 저널 꼬리는 **한 번만** 읽는다. 우리가 그 구역에서 쓰지 않았다면 꼬리는
> 변하지 않으므로, 그 구역의 읽기 지점들이 같은 값을 나눠 쓴다.

`ConversationJournal.append()` 가 호출자가 읽은 꼬리를 **인자로 받는다**(같은 seq 판정을 두 번 하지 않는다).
미결 꼬리(truncated)를 들고 오면 신뢰하지 않고 다시 읽는다(seq 오부여 방지).

### 3-2. 구현(패처 `patch_flush_budget.py` · 훅 6개 · 2파일)

| # | 파일 | 변경 |
| --- | --- | --- |
| 1 | `conversation_journal.py` | `append(event, *, tail: JournalTail \| None = None)` — 호출자의 꼬리를 받는다 |
| 2 | `conversation_store.py` | `self._tail_memo: tuple[str, Any] \| None` 한 칸 기억 추가 |
| 3 | `conversation_store.py` | `_cross_process_lock()` **진입**에서 기억을 비운다(구역이 바뀌면 낡았다) |
| 4 | `conversation_store.py` | `_journal_tail(journal, *, fresh=False)` 도우미 |
| 5 | `conversation_store.py` | `_authoritative_record` · `_reconcile_view_with_journal` · `_commit_event` 가 도우미를 쓴다 |
| 6 | `conversation_store.py` | 우리가 저널에 쓴 직후(`_commit_event`) 기억을 비운다 |

`fresh=True` 는 **미결 꼬리를 옮긴 뒤**에만 쓴다(그때는 파일이 실제로 변했다).

**왜 안전한가**: 기억의 수명은 **한 flock 임계 구역**이다. 구역 안에서 꼬리를 바꿀 수 있는 것은 우리뿐이고
(다른 프로세스는 flock 을 못 잡는다), 우리가 바꾸면 그 자리에서 비운다. 구역이 바뀌면 진입에서 비운다.

### 3-3. 기대 효과(측정된 기준선 기준)

| 항목 | 종전 | F1 뒤 | 근거 |
| --- | --- | --- | --- |
| `tail()` 호출/append | 3.00 | **1.00** | 계약 시험 ① |
| 읽은 바이트/append | 116,025 B | **≈38,700 B** | 계약 시험 ① |
| `os.open`/append | 5.00 | **≤ 4** | 계약 시험 ③ |
| `os.fsync`/append | 1.00 | **1.00 (불변)** | 계약 시험 ② |

시간 환산은 **하지 않는다** — 꼬리 읽기 비용은 페이지 캐시에서 오므로 디스크 상태에 흔들리는 값이고,
이 배치의 근거는 **개수**다(§0 의 교훈).

### 3-4. 이빨 — 계약 시험 9개(`test_flush_budget_contract.py`)

| # | 문장 |
| --- | --- |
| ① | append 1회는 꼬리를 **한 번만** 읽는다(재읽기 ≤ 70 KB) |
| ② | append 1회의 `fsync` 는 **정확히 1회**(배치가 내구성을 못 바꾼다) |
| ③ | `open` 예산이 늘지 않는다(≤ 4.5) |
| ④ | `revision`/`seq` 는 append 1회에 1씩만 오른다 |
| ⑤ | **낡은 꼬리 기억을 절대 재사용하지 않는다**(CAS 실패 + 타 writer 전진 뒤에도 revision 이 겹치지 않는다) |
| ⑥ | 미결 꼬리는 종전과 똑같이 **커밋 전에** 옮겨진다 |
| ⑦ | 커밋 **순서**가 그대로다 — 줄 + `fsync` 가 먼저, view 교체가 다음(ADR §2) |
| ⑧ | view 쓰기가 실패해도 저널 커밋은 살아남고 원본이 복구된다 |
| ⑨ | 기억을 비우는 지점이 **임계 구역 진입**에 있다(소스 이빨) |

> ⚠ **이 시험 파일은 적용 전에는 의도적으로 빨갛다(3 failed).** 그게 “이빨이 문다”는 증거다(P1).
> 그래서 넓은 `docs/` 전수 실행에 섞지 말고 **명시 경로**로 돌리고,
> `NX10_FLUSH_TREE=<트리>` 로 검사 대상을 고정한다. 승격(`tests/`) 뒤에는 그 트리에서 전부 초록이다.

### 3-5. 리허설(미러 · 본 트리 쓰기 0건) — **ALL PASS 16/16**

| 시나리오 | 결과 |
| --- | --- |
| P1 적용 **전** 이빨 | **3 failed**(꼬리 예산 · open 예산 · 소스 이빨) — 시험이 조용히 통과하지 않는다 |
| P2 적용 → 승격 위치 검증 | 계약 시험 **9 passed** · ruff OK · **basedpyright 0 errors** |
| P2b 승격 위치에 타입 결함 | 정적 검사가 잡고 **롤백**(사전 이미지 복원) |
| P3 기존 계약 시험 무회귀 | **70 passed**(journal · retention · CR-01 identity · FR-05 authoritative · multiprocess) |
| P4 동결/소크 가드 | 돌고 있는 실행을 만나면 **exit 9** · PERF 미승격 트리에는 **exit 6** |
| P5 사전 이미지 불일치 | **거부**(exit 8) · 쓰기 0건 · 백업 안 남김 |
| P6 본 트리 무변경 | `src/` 두 파일 sha256 전후 동일 · 시험·백업 미생성 |

리허설이 **거짓 FAIL 2건**을 실제로 만들어 냈고, 둘 다 도구 쪽 교훈으로 남겼다:
① 저장소 루트에서 절대경로로 정적 검사를 돌리면 임포트 해석이 **진짜 `src/`** 를 집어 미러의 새 시그니처를
못 보고 “No parameter named tail” 을 **거짓으로** 보고한다 → 정적 검사는 **그 바이트를 소유한 뿌리**에서 돈다.
② `basedpyright` 는 **경고만 있어도 exit 1** 이다(errors 0 · warnings 116 · exit 1 실측) → 판정은 종료 코드가
아니라 **파싱한 `errorCount`** 로 한다(안 그러면 깨끗한 패치를 롤백한다).

## 4. F2 — view 재작성 스로틀(설계만 · 오너 결정)

### 4-1. 사실

매 append 마다 view 전체를 다시 쓴다: **8,021 B 직렬화 + 1 open/write/close + 1 `os.replace`**. ADR §2 는
이미 **view 가 뒤처져도 된다**고 적었다 — “If the view refresh fails, the journal stays authoritative and the
view is rebuilt from it”. 즉 스로틀은 **ADR 안에 있는 여지**다.

### 4-2. 제안

`_persist` 를 **N회 또는 T초마다**로 제한하고, 읽기 표면은 기존 `_reconcile_view_with_journal`(view 가
journal 보다 뒤처지면 재생성)을 그대로 쓴다. 후보 노브: `AGK_CONVERSATION_VIEW_REFRESH = immediate|coalesced`.

### 4-3. 결정해야 할 것(D-F2)

1. 읽기 표면의 **신선도 계약**(“방금 쓴 턴이 view API 에 즉시 보이는가”)을 어디까지 늦출 것인가.
2. 지금 `_authoritative_record` 가 journal 을 읽으므로 **쓰기 경로의 정확성**은 영향받지 않는다 — 영향을 받는
   것은 **표시**다. 그 문장을 계약 시험으로 고정할 수 있는가.
3. 효과는 **8 KB + rename 1회/append** 인데, 이건 결정적이다(디스크 상태 무관). 즉 F1 과 같은 성격의 이득을
   계약 변경 비용으로 산다 — 순서를 F1 뒤로 두는 이유다.

## 5. F3 — sync 정책(설계만 · ADR 개정 필요)

### 5-1. 왜 별도 배치인가

현재 계약은 **문장**이다: *“One mutation = append the record line + `fsync` … Only events whose journal line is
durably committed may appear in the view”*(ADR-DAT-02 §2). `batched` 를 기본값으로 만들면 **그 문장을 고쳐야**
한다 — 코드 변경이 아니라 **약속의 변경**이다. 그래서 제안만 하고 오너 결정을 기다린다.

### 5-2. 후보 셋과 각각의 대가

| 후보 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| `always`(현행) | 커밋 = 즉시 내구 | 없음(현행) |
| `batched` | N회/T ms 에 1회 sync → fsync 호출 **1/N** | 크래시 시 **마지막 창**의 턴 유실(§5-3 의 문구가 필요) |
| `fdatasync`(Linux) | 크기 메타데이터 sync 생략 — 싸다 | **이 플랫폼엔 없다**(macOS 실측 False). 플랫폼 분기 필요 |

### 5-3. `batched` 를 택한다면 함께 정해야 하는 문장(그대로 ADR 개정 초안이 된다)

- 유실 창의 정의: **“가장 최근 성공한 sync 이후의 커밋은 크래시에서 사라질 수 있다”**(창 = N회 또는 T초).
- 창을 **관측 가능**하게: 상태 노출(`sync_pending`, 마지막 sync 시각)과 셧다운 시 `flush()`.
- **줄 자체는 항상 먼저 쓴다**(순서 보존) — 유실은 “사라짐”이지 “뒤바뀜”이 아니다.
- 리더는 **동기화 여부를 알 수 없어도** 재생 결과가 일관되다: 읽히는 줄은 모두 유효하고, 미결 꼬리 규칙은 그대로다.
- macOS 에서 “durable” 이 무엇을 뜻하는지 명시(`os.fsync` ≠ `F_FULLFSYNC` — §1-2). 지금 문구는 그 구멍을 덮고 있다.

## 6. 적용 순서·가드·되돌림

### 6-1. 순서(전부 지문을 움직인다 → **맨 마지막**)

```
4차 soak 회수 → 3차 배치 → SC6 → PERF → [게이트 23개 재측정] → **FLUSH(F1)** → 게이트 재측정 → 새 지문 8시간 soak
```

이 배치가 바꾸는 것은 `src/` — 지금 돌고 있는 4차 soak 의 **지문 대상 그 자체**다. 그래서
`apply_flush_batch.sh` 는 ① 돌고 있는 soak 을 만나면 **exit 9** ② PERF 가 아직 승격되지 않았으면 **exit 6**
③ 사전 이미지가 다르면 **exit 8** 로 멈춘다(전부 **쓰기 0건**).

### 6-2. 가드 요약

| 가드 | 조건 | 종료 |
| --- | --- | --- |
| 동결 | `pgrep val02_staging.py` 가 잡히면 | **9** |
| 합성 순서 | `scripts/val02_staging.py` 에 사다리(`NX10_DEEP_PROFILE`)가 없으면 | **6** |
| 사전 이미지 | 두 파일 sha256 이 고정값과 다르면 | **8** |
| 검증 | py_compile · ruff · basedpyright `errorCount != 0` 이면 **자동 롤백** | **5** |

### 6-3. 되돌림

`patch_flush_budget.py --root <트리> --revert` — 백업(`*.preflush.bak`)에서 복원한다. 적용 스크립트는
성공하면 백업을 지우므로, 되돌림이 필요하면 **적용 전 커밋**을 기준으로 되돌린다(이 프로젝트의 규칙:
지문 대상 변경은 커밋 단위로 되돌린다).

---

## 7. 오너에게 올리는 결정

- **D-F1** F1(꼬리 1회 읽기) 승인 — 계약·내구성 변화 **없음**. 거절할 이유를 찾기 어렵지만, 지문 대상이라
  순서(§6-1)만 지키면 된다.
- **D-F2** view 재작성 스로틀(8 KB + rename/append 절감)을 할 것인가 — 한다면 **읽기 신선도 계약**을 어디까지
  늦출지 정해야 한다(권고: 쓰기 경로는 `_authoritative_record` 가 journal 을 읽으므로 정확성은 불변 ·
  표시만 지연).
- **D-F3** sync 정책을 바꿀 것인가 — 바꾼다면 **ADR-DAT-02 §2 개정**이 선행이다(§5-3 문구). 권고 **보류**:
  지금 성능 문제는 §3 의 예산으로 대부분 사라지고, 유실 창은 **되돌릴 수 없는** 결정이다.
- **D-F3′** “durable” 의 플랫폼별 정의를 ADR 에 명시할 것인가(macOS `F_FULLFSYNC`).
- **D-F4** 적용 시점 — 이 배치는 **GA 후보를 다시 재게 만든다**(게이트 23 + 8시간 soak). 지금 후보를 GA 로
  보낼 것인지, 이 배치를 후보에 넣고 다시 잴 것인지.

---

## 8. 남는 한계(먼저 적는다)

1. **F1 의 효과는 개수로만 말한다** — 시간 절감은 디스크 상태에 달려 있어 주장하지 않는다(§0).
2. **fsync 자체는 그대로 1회다** — 이 배치는 §0 의 300~350 µs 고정세를 줄이지 않는다. 그건 F3 의 몫이다.
3. **F2·F3 은 설계만** — 코드도 시험도 없다(오너 결정 뒤 별도 배치). 계약 시험을 먼저 쓸 수 없기 때문이다
   (무엇을 보장할지가 정해지기 전에는 문장이 없다).
4. **리허설은 미러**다 — 실제 적용은 게이트 재측정·8시간 soak 까지 가야 판정이 된다.
5. **`os.fsync` 는 macOS 에서 미디어 보장이 아니다** — 지금 “커밋 = 줄 + fsync” 문장은 그 사실을 덮고 있다(§5-3).

## 10. F2·F3 을 **배치로** 만드는 조건 — 오너 결정이 서면 바로 적용할 수 있도록

§4·§5 는 “무엇을 바꿀 것인가”를 적었다. 이 절은 “결정 뒤 어떻게 같은 방식의 배치로 만드는가”다. 셋을 같은
틀(F 번호 = 배치 번호 · 사전 이미지 고정 · 가드 셋 · 승격 위치 정적 검사)로 만들어야 승인이 오늘 안으로 적용된다.

### 10-1. 대안 비교 — 오너가 고르는 표

| 배치 | 무엇 | 이득(측정 근거) | 대가 | 선행물 | 준비도 |
| --- | --- | --- | --- | --- | --- |
| **`FLUSH`(=F1)** | 꼬리 3회 → 1회 | `tail()` 3.00→1.00 · 113 KiB→≈38 KiB · `open` 5.00→≤4 | **없음**(계약 불변) | 없음 | **스테이징+리허설 16/16 진짜코드 준비 완료** |
| **`FLUSH2`(=F2)** | view 재작성 스로틸(옵트인) | 400턴 실측: 재작성 **402→52회** · 다시 쓴 바이트 **5.6→0.70 MB** · 재생 **0**(결정적) | **읽기는 안 늦는다**(계약 C-1) — 다른 프로세스의 첫 읽기가 재생 1회 | D-F2 **답함**(계약) | **스테이징+리허설 21/21 완료** |
| **`FLUSH3`(=F3)** | sync 정책 `batched`/`fdatasync` | `fsync` 호출 **1/N**(§0 의 300~350 µs 고정세에 직접) | 크래시 시 **마지막 창 유실** — 되돌릴 수 없는 약속 변경 | **ADR-DAT-02 §2 개정 머지** 먼저 | ADR 초안 재료는 §5-3 에 문장 단위로 준비 |

> 순서를 **굳이** 나열하면 F1 → F2 → F3 이다: F1 은 계약을 안 건드리고, F2 는 개수를 줄이며(계약 영향 = 표시),
> F3 은 **계약 자체**를 바꾼다. 승인을 한 문장씩 받을 수 있는 순서다.

### 10-2. `FLUSH2` — **결정·구현·리허설 완료**(오너 지시 2026-09-17 — 신선도 계약)

오너 지시(“신선도 계약을 정하고 계약 시험으로 옮겨 둬”)가 와서 F2 는 **설계에서 배치로 넘어갔다**: 계약 전문은
[fsync2/VIEW_FRESHNESS_CONTRACT.md](../fsync2/VIEW_FRESHNESS_CONTRACT.md) · 스테이징 `nx10/fsync2/` ·
훅 12개(모두 `conversation_store.py`) · 계약 시험 **10건** · 미러 리허설 **ALL PASS 21/21**.

**정한 문장(요약)**: *읽기는 늦추지 않는다(C-1) · 지연 판정은 mtime 이 아니라 시퀀스(C-2) · 창은 유한하고
기본은 현행(C-3·C-6) · 따라잡기는 저널을 다시 읽지 않는다(C-4) · 수렴점이 있고(C-5) 읽기가 그 자리에서
수렴하며(C-7) 삭제는 되살리지 않는다(C-8).*

이 조사가 **두 개를 바꿨다**: ① 종전 mtime 판정은 실측으로 **거짓**이었다(옛 view + 새 mtime → 읽기가 커밋된 턴
2개를 놓쳤다) — 스로틸과 무관하게 닫아야 할 구멍이다. ② “쓰기를 k회에 1회로 미루자”는 **회귀**였다(미룸당
저널 전체 재생 1.17회 — 8시간 soak 의 저널 크기에서 하루 실패를 냈던 그 부류). 그래서 C-2·C-4 가 계약의 본체다.
기대 효과(결정적·실측): 400턴에서 view 재작성 **402 → 52회**(1/8) · 다시 쓴 바이트 **5.6 MB → 0.70 MB** ·
저널 재생 **0** — 같은 400턴에서 저널이 110 KB 자라는 동안 view 는 5.6 MB 를 다시 썼다(표시용이 내구 기록보다
**약 51배** 많이 쓴다).

**합성 순서**: 사전 이미지가 **F1 적용 뒤** 바이트(`conversation_store.py c9029151ccbd…`)라 F1 없이 돌리면 `exit 8`.
적용 순서는 `FLUSH`(F1) → **`FLUSH2`(F2)** 이고, 둘 다 지문을 움직이므로 `PERF` 뒤 · 뒤이어 게이트 재측정·새 8시간 soak.

### 10-3. `FLUSH3` 를 배치로 만들 때 — 약속이 먼저, 코드가 다음

**선행물(코드보다 먼저 머지)**: §5-3 의 여섯 문장을 ADR-DAT-02 에 넣는다 — 특히 ① 유실 창의 정의
② `sync_pending`·마지막 sync 시각으로 창을 **관측 가능**하게 ③ **줄은 항상 먼저**(유실이지 뒤바뀜이 아니다)
④ 셧다운 `flush()` 보장 ⑤ macOS 에서 “durable” 의 뜻(`os.fsync` ≠ `F_FULLFSYNC` — §1-2 실측 근거).

그 뒤 훅: 정책 객체(`always`/`batched(N,T)`/`fdatasync`)를 `_commit_event` 에서 쓴다 · 플랫폼 능력 탐지
(`hasattr(os,"fdatasync")`)로 **없으면 조용히 `fsync` 로 강등하고 그 사실을 리포트에 남긴다** · 기본값은
`always`(개정 문장이 기본을 바꾸라는 결정을 하기 전까지는 현행). 계약 시험 후보: ① `always` 는 append 당 정확히
1회 ② `batched` 는 N회에 1회이고 그때도 **줄이 먼저** ③ 창이 관측된다(`sync_pending` 내려간다) ④ `flush()` 뒤
0 ⑤ `fdatasync` 없는 플랫폼에서 강등이 일어나고 리포트에 적힌다 ⑥ **크래시 시뮬레이션**: 마지막 창의 커밋이
사라져도 재생 결과가 **일관**(읽히는 줄은 모두 유효 · 미결 꼬리 규칙 불변). 되돌림은 노브 한 줄(`always`)이다.

### 10-4. ④가 적용되면 지문에 무엇이 일어나는가(계획으로 미리 적어 둔다)

같은 틀을 세 번 밟으므로 미리 적는다: ① **게이트 23개 재측정**(약 16분) ② **새 지문에서 8시간 soak**
③ 회수 → 커밋. 그리고 `FLUSH` 는 `PERF` 가 넣은 **처리량 축과 사다리를 가진 하네스**를 돌리므로, 그 8시간은
처음으로 “SC-6 새 기준 + 처리량 축 + 네 칸 사다리”가 **한 지문에서** 돈다(사다리는 회귀가 없으면 `not_applicable`
로 끝난다 — 그러면 그 칸들은 다음 회귀 때 처음 태워진다).
